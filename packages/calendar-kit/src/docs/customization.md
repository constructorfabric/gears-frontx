# Customization

There are eight ways to change the calendar, from global to local. Use the highest one that does the job: a token change restyles every component at once; a render slot changes one part of one component.

| Level | Changes | Use it for |
| --- | --- | --- |
| [1. Theme tokens](#1-theme-tokens) | Colours, fonts, spacing, radii, sizes everywhere | Matching a design system |
| [2. Colour scheme and modes](#2-colour-scheme-dark-mode-and-system-modes) | Light, dark, forced colours, reduced motion | Dark mode, accessibility settings |
| [3. Behaviour props](#3-behaviour-props) | What a component shows and allows | Five-day weeks, 30-minute slots, read-only screens |
| [4. Text](#4-text) | Any label, announcement or message | Wording, translation |
| [5. Classes and DOM hooks](#5-classes-and-dom-hooks) | Styling one part of one component | Striping cells, highlighting a column |
| [6. Render slots](#6-render-slots) | The content of one part | Product-specific cards, cells, headers |
| [7. Composition](#7-composition) | Which pieces appear and where | Your own side panel, your own dialog shell |
| [8. Headless](#8-headless) | Everything; you render the markup | A layout the components cannot produce |

## 1. Theme tokens

Every colour, font, space, radius and control size in the kit is a `--cal-*` custom property, and each one reads an **upstream seam**: a plain custom property such as `--surface`, `--primary` or `--font-sans`. Define the seams on any ancestor of the calendar and every component follows.

```css
.calendar-root {
  --surface: var(--my-ds-background);
  --foreground: var(--my-ds-text);
  --primary: var(--my-ds-brand);
  --font-sans: var(--my-ds-font);
  --radius-md: 6px;
}
```

Or import the OneCloud preset, which sets every seam for light and dark. The full seam list with defaults and preset values is in [Theming](../styles/theming.md).

Tokens are the only supported way to recolour components. Kit class names are generated by CSS Modules and change between releases.

## 2. Colour scheme, dark mode and system modes

- **Explicit:** set `data-theme="dark"` or `data-theme="light"` on the calendar root, any ancestor, or the shadow host.
- **System:** without `data-theme`, the kit follows `prefers-color-scheme`. `data-theme="light"` opts out of that.
- **Forced colours** (Windows high contrast): the theme remaps surfaces, text, focus and selection to system colours automatically.
- **Reduced motion:** every transition duration drops to zero when `prefers-reduced-motion: reduce` is set.

Overlays (popovers, dialogs, the create form) portal out of the component that opened them: into the shadow root when there is one, otherwise next to their trigger. Put `data-theme` where overlays inherit it too: on `<html>`, or on the shadow host, which the theme matches through `:host([data-theme])`. `container` places an overlay inside a specific element instead; see the [shadow-root recipe](recipes.md#inside-a-shadow-root).

## 3. Behaviour props

| Component | Props |
| --- | --- |
| `WeekGrid` | `visibleDays` (5 or 7), `visibleHours`, `slotMinutes`, `workingHours`, `interactionMode`, `trailingGutter`, `now` |
| `DayGrid` | `visibleHours`, `slotMinutes`, `workingHours`, `interactionMode`, `trailingGutter` |
| `MonthGrid` | `selectionMode` (`date-range`), `weekNumbering` (`iso`), `monthData.densityCap`, `trailingGutter`, `now` |
| `CalendarToolbar` | `availableViews` (which views, in which order) |
| `EventCard` | `positioned`, `selected`, `past`, `available`, `readOnly` |
| `EventDetailPanel` | `anchorElement` (popover or dialog), `comparisonTimeZone`, `maxVisibleParticipants`, `readOnly` |
| `CreateEventPopover` | `expanded`, `anchorRect` / `anchorRef` |
| `ConflictIndicator` | `compact` |
| `AvailabilityGrid` | `interactionMode` (`read-only`) |
| `WorldClocks`, `MonthNavigator`, `SearchResults` | `now` |

Turning a feature off usually means leaving its callback out: without `onEdit` there is no edit button, without `onCreateCalendar` no create button, without `onQuickCreate` an empty slot does nothing.

## 4. Text

Every string the kit generates has a stable translation id and English text. Change it at three levels:

```tsx
<CalendarLocalizationProvider
  t={hostTranslate}
  messages={{ en: { "calendar.toolbar.today": "Now" } }}
>
  <WeekGrid
    translations={{ "calendar.week.range": "Showing week of" }}
    {...props}
  />
</CalendarLocalizationProvider>
```

A component's `translations` wins over everything, then your `t`, then the provider's catalogue from `messages`, then English. The full order and the catalog are in [Internationalization](i18n.md) and the [translation catalog](messages.md). Your own content (titles, locations, metadata, slot output) is never passed through `t`.

## 5. Classes and DOM hooks

Every component root accepts `className`. The grids also take classes for their parts:

| Component | Part classes |
| --- | --- |
| `WeekGrid`, `DayGrid` | `cellClassName`, `columnHeaderClassName`, `gutterClassName` |
| `MonthGrid` | `cellClassName`, `columnHeaderClassName`, `weekNumberClassName` |

These are the stable styling hooks. Kit CSS Module classes are not.

Stable attributes you can select on:

| Attribute | Where | Meaning |
| --- | --- | --- |
| `data-event-id` | every rendered event | The event's `id` |
| `data-event-card-layout` | `EventCard` | Density tier: `full`, `stacked`, `single` or `title` |
| `data-slot-time` | `AgendaView` time stamps | The slot's time |
| `data-agenda-metadata` | `AgendaView` metadata rows | Which fact the row holds: `timing`, `organizer`, `attendees` |
| `aria-pressed`, `aria-disabled` | events | Selected; unavailable or busy |
| `aria-selected` | `MonthGrid` days in `date-range` mode | The day is inside the range |
| `aria-current="date"` | `SearchResults` group heading | Today's group |

```css
.my-week [data-event-id] {
  box-shadow: none;
}
.my-week [data-event-card-layout="title"] {
  font-weight: 600;
}
.my-month [aria-selected="true"] {
  outline: 2px solid var(--primary);
}
```

## 6. Render slots

A render slot replaces the content of one part and keeps the kit's positioning, focus and keyboard behaviour around it. Slots receive typed contexts, never DOM nodes.

| Component | Slots |
| --- | --- |
| `WeekGrid` | `renderEvent`, `renderConflict`, `renderDetail`, `renderCell`, `renderUnavailable` |
| `DayGrid` | `renderEvent`, `renderConflict`, `renderCell` |
| `MonthGrid` | `renderEvent`, `renderCell`, `renderOverflow` |
| `AgendaView` | `renderEvent`, `renderDayHeader` |
| `EventCard` | `renderTitle`, `renderTime`, `renderMetadata`, `renderConflict` |
| `EventDetailPanel` | `renderHeader`, `renderBody`, `renderMetadata`, `renderActions`, `renderFooter` |
| `CreateEventPopover` | `renderHeader`, `renderFields`, `renderFooter`, `renderError`, `renderCompactShell`, `renderExpandedShell` |
| `CalendarToolbar` | `renderTitle`, `renderViewOption`, `renderLeading`, `renderTrailing` |
| `ConflictIndicator` | `renderConflict` |
| `AvailabilityGrid` | `renderCell` |
| `MonthNavigator` | `renderDay`, `renderHeader` |
| `SearchResults` | `renderResult`, `renderGroupHeader` |
| `TimeZoneList` | `renderOption` |
| `WorldClocks` | `renderClock`, `renderEditor` |
| `CalendarList` | `renderCalendar`, `renderCreateCalendar` |
| `CalendarSidePanel` | `slots.header`, `.search`, `.body`, `.monthNavigator`, `.timeZones`, `.worldClocks`, `.calendarList`, `.searchResults` |
| `CalendarGrid` | `renderCell`, `renderHeader` |

Tips:

- **Keep the kit card, change one part.** Inside `renderEvent`, render `EventCard` with `positioned={false}` and your own `renderMetadata`. You keep density tiers, states and accessibility. See the [custom rendering recipe](recipes.md#custom-event-rendering).
- **Type your metadata once.** `WeekGrid<MyMetadata>` makes every slot context typed.
- **Slots should not be interactive** unless they own their own keyboard handling. The kit's event element is already a button; a nested button inside it is invalid HTML.
- **Define slot functions outside render** or memoize them when they are expensive; they run for every visible event.

## 7. Composition

The larger components are assembled from the smaller ones, and you can reassemble them:

- `CalendarSidePanel` is a shell around `MonthNavigator`, `SearchResults`, `TimeZoneList`, `WorldClocks` and `CalendarList`. Replace any section through `slots`, or skip the shell and place the pieces in your own layout.
- `CreateEventPopover` renders in the kit's popover and dialog by default. `renderCompactShell` and `renderExpandedShell` hand you the form content to put in your own container.
- `EventDetailPanel` opens as a popover when you pass `anchorElement` (the third argument of `onEventSelect`) and as a dialog without one.
- `EventCard` and `ConflictIndicator` work outside the grids, for example in a list or a notification.

## 8. Headless

Every component's state and behaviour is a hook exported from `@gears-frontx/calendar-kit/react`: `useWeekGridController`, `useMonthGridController`, `useCreateEventController` and so on. Use one to render your own markup with the kit's layout, keyboard model and state handling. See [Headless controllers](headless.md).

## What you cannot customize, and why

- **Internal class names.** CSS Module names are private so the kit can restructure markup without breaking hosts. Style through tokens, part classes and the attributes above.
- **Grid geometry.** The hour row height (43px) and the one-line event strip height (21px) are fixed because layout math in TypeScript depends on them. They are single-sourced constants, checked against the CSS by a test.
- **Week start.** Week and month grids start on Monday; `MonthNavigator` starts on Sunday.
- **Scheduling decisions.** Conflicts, availability and permissions are always the host's input.

If one of these blocks you, open an issue describing the use case; widening a contract is a deliberate change.
