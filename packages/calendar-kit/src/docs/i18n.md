# Internationalization

The kit ships every string it generates with a stable translation id and English text. Your app chooses the language, loads translations and hands the kit a translator. The kit never imports an i18n library.

## The pieces

| Setting | Controls | Default |
| --- | --- | --- |
| `locale` | Date, time and number formatting, plural rules, direction | `en-US` |
| `direction` | `ltr` or `rtl`: layout mirroring and arrow-key direction | the direction of `locale` |
| `t` | Your translator for kit translations | the built-in English |
| `messages` | Catalogues by locale, walked through the locale chain (provider only) | none |
| `translations` | Text for the active locale, used in place of the provider's (component only) | none |
| `onMissingTranslation` | Called once per id nothing could resolve (provider only) | none |

`timeZone` is not localization: it lives on `CalendarProvider`.

## Setting them once

```tsx
import {
  CalendarLocalizationProvider,
  CalendarProvider,
} from "@gears-frontx/calendar-kit";

<CalendarProvider timeZone={viewerTimeZone}>
  <CalendarLocalizationProvider
    locale={i18n.language}
    direction={i18n.dir()}
    t={(id, values) => i18n.t(`calendar:${id}`, values)}
    messages={{ de }}
  >
    <CalendarScreen />
  </CalendarLocalizationProvider>
</CalendarProvider>;
```

Every kit component below the providers uses these values. A nested provider inherits whatever it does not set from the outer one, so a panel can switch to another zone without restating the translator. `direction` is derived from `locale` until you set it explicitly; once set it is inherited like any other value.

## Per-component overrides

Every component accepts `locale`, `timeZone`, `direction`, `t`, `translations` and `className` directly. A prop on a component wins over the provider for that component only:

```tsx
<MonthNavigator timeZone={comparisonZone} {...props} />
<WeekGrid translations={{ "calendar.week.range": "Showing week of" }} {...props} />
```

## How a translation is resolved

For each kit translation the resolver tries, in order:

1. the component's own `translations`
2. your `t`
3. the provider's `messages`, walking the locale chain (`pt-BR` → `pt` → `en`)
4. the built-in English

A result that is empty, missing, or equal to the id itself counts as a miss and moves to the next layer. That is why returning the key from your translator when you have no text is safe: the user sees English, never `calendar.week.range`. If even English has nothing (an id the kit does not define), `onMissingTranslation` fires once for that id and the user sees "Translation unavailable".

A component's `translations` outrank your `t` so a single component can be retexted in place; the provider's catalogues lose to it so a host that already translates everything keeps ownership.

A catalogue is keyed by locale, so switching language is one prop:

```tsx
<CalendarLocalizationProvider locale={locale} messages={{ "pt-BR": ptBR, pt }}>
```

`pt-BR` reads `pt-BR`, then `pt`, then the bundled English, per id. The locale is canonicalised first, so `pt_BR` and `pt-br` read the `pt-BR` catalogue, and a script is its own step: `zh-Hant-TW` reads `zh-Hant` before `zh`. Each catalogue picks its plural form with its own language's rules, so an English fallback always reads `0 events`. Only a component takes `translations`, and only flat: it renders in exactly one locale, so an override written for another one would be a bug.

## Values and plurals

Templates use named placeholders: `{{count}}`, `{{date}}`, `{{weekdays}}`. Your `t` receives the raw values: counts stay numbers, so your library applies its own number and plural formatting. The kit formats them itself only when it reads a value from `translations`, `messages` or English.

Plural templates carry an i18next suffix, `_one` and `_other`. **The kit passes your `t` the base id and a numeric `count`, never a category-suffixed id**, so a react-i18next host picks the form itself:

```ts
t("calendar.month.eventCount", { count: 2 });
```

```json
{
  "calendar.month.eventCount_one": "{{count}} event",
  "calendar.month.eventCount_other": "{{count}} events"
}
```

A translation may use any CLDR categories its language needs (`_few`, `_many`, …); a category it does not carry falls back to `_other`, then to the bare id. When a language spells every count the same way — `{{count}} awaiting` — one bare id is enough: the lookup falls through the missing suffixes to it, and so does react-i18next.

## Your content is not translated

Event titles, locations, organizer names, conflict dimensions and labels, `metadata`, and anything a render slot returns are your content. The kit shows them as given and never passes them through `t`.

## Right-to-left

`direction="rtl"` mirrors the layout with CSS logical properties and swaps the meaning of the Left and Right arrow keys in every grid and list. Vertical keys keep their meaning. Derive the direction from the locale for the document itself:

```tsx
import { getLocaleDirection } from "@gears-frontx/calendar-kit";

<html lang={locale} dir={getLocaleDirection(locale)}>
```

## Finding translation ids

The [translation catalog](messages.md) lists every id with its English text and placeholders. Each component reference lists the ids it uses.

## Tips

- **Namespace the ids in your dictionary** (`calendar:calendar.week.range`) so kit ids cannot collide with your own.
- **Ship partial translations.** Anything missing falls back to English.
- **Log misses in development.** `onMissingTranslation={(id) => console.warn(id)}` catches ids you forgot, but only those English cannot fill; translate against the catalog to find the rest.
- **Test with a pseudo-locale** that wraps every value (`t={(id) => \`⟦${id}⟧\`}`) to see which text comes from the kit and which from your content.
