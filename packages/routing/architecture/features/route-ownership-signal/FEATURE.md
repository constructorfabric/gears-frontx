## 1. Feature Context

- [ ] `p2` - `cpt-frontx-feature-routing-route-ownership-signal`

### 1.1 Overview

Route Ownership Signal publishes, rather than enforces, small independent facts derived from the URL at one domain, and orchestrates no mounting. It has three parts, all scoped to a single domain key at a time. First, **entry resolution**: given every entry the current location carries under one domain key and that domain's own set of registered extensions, it names, for each such entry, the route owner its extension token resolves to, or reports the entry as unresolved when no registration matches — a primitive every observer runs internally, not a public entry point of its own (DESIGN §3.2, Route Ownership Signal). Second, an **observer** the consumer creates once per domain — passing that domain's own registered-extensions source as a plain argument, never an injected port, together with that domain's own key: it subscribes to the navigation substrate's shared history and, on creation and on every subsequent navigation, reports one *transition* — the ordered list of entries currently carrying that domain key, resolved or unresolved, together with a diff against the previous report distinguishing entries added, removed, changed only in payload, reordered, or changed only in resolution status (an entry moving between resolved and unresolved with its own token and payload unchanged) — or no transition at all when the ordered list and its resolutions are unchanged, which is also what a navigation touching only a foreign domain key or the hash produces, since resolution reads only the entries carrying this domain's own key. Creating the observer also returns a release function the consumer calls to stop it. Third, a **URL back-projection helper** the consumer calls to reflect into the URL each `mount_ext` or `unmount_ext` execution the runtime reports as settled: it replaces that one domain's own entries with the caller's given delta — entries added (appended at the end of the full list), removed (leaving no gap), changed only in payload (in place, at their existing position), replaced (an existing entry's own extension token swapped for a new entry at that same position), or reordered (this domain's own entries taking a new relative order within the set of positions they already occupy) — removes, in that same single history write, every entry under each domain key the delta's `clearedDomainKeys` names (structural reset: the exact nested routed domains the caller knows leave with an extension the delta removes or replaces), and copies everything else — including every entry under the same domain key that the delta does not name — verbatim. The helper infers no domain key to clear from any key's shape or from a lexical prefix: a domain key is the domain's own declared route, a single `name` carrying no ancestry (`cpt-frontx-routing-adr-domain-occupancy-addressing-granularity`), so which domains nest in a departing extension's zone is a fact only the caller holds. None of the three touches mounting, unmounting, a registry of route owners, or a state machine tracking which owner currently occupies a domain — those facts and that occupancy belong entirely to the `mfes` runtime, which the framework router reaches only through `mount_ext` and `unmount_ext` actions.

Resolving a URL several domains deep is a wave through the tree of domains, not one event: each domain's own observer resolves and reports independently the moment that domain comes to exist, reading whatever the shared history's `location` already is at that moment, never a value captured earlier. This package holds no registry of domains and publishes no signal asserting that a whole address resolved end to end — it cannot, by construction, since it never sees the tree the framework router and the runtime assemble from each domain's own report. A domain resolving to no entries at all is, for exactly this reason, indistinguishable from "the wave has not reached this domain yet" until that domain's own observer comes to exist and reports.

In a composed application the consumer of the observer and of the back-projection helper, for every routed domain, is the framework router (`cpt-frontx-routing-actor-framework-router`): the router the template framework provides to implement the runtime's router port (`cpt-frontx-adr-extension-routing-port`). Throughout this FEATURE, *the consumer* names it. An occupant's own engine provider also calls the back-projection helper, to write that occupant's own entry's own parameters as a payload change (`cpt-frontx-feature-routing-engine-provider`); it never names an addition, a removal, a replacement, a reorder, or a domain key to clear.

### 1.2 Purpose

A composed application's routable domains must resolve the same way regardless of how the user arrived at a URL — typing it, reloading it, stepping back or forward through history, or following a link — and that must hold at every domain a composed application actually nests, not only at the outermost one, and at every occupant count a domain's own occupancy strategy admits, not only a single occupant. But the runtime that actually owns domain occupancy — named mount strategies, a cardinality matrix, and a registry of what is currently mounted — is the `mfes` runtime, not this library, and it changes occupancy only by executing `mount_ext` and `unmount_ext` actions; the full boundary this draws is owned by `cpt-frontx-routing-principle-publishes-not-orchestrates` (DESIGN §2.1), not repeated here. Route Ownership Signal exists to give the framework router — the party that pursues agreement between the URL and the mounts, in both directions, for every routed domain (`cpt-frontx-adr-extension-routing-port`, URL ownership) — the URL-derived facts it turns into action chains, and the one write path through which it reflects each settled action back into the URL, at whatever depth and whatever occupant count a domain has, without this package ever holding, orchestrating, or guessing at that reconciliation itself.

**Requirements**: `cpt-frontx-routing-fr-route-ownership-signal`, `cpt-frontx-routing-fr-concurrent-occupant-projection`, `cpt-frontx-routing-fr-per-occupant-addressable-parameters`

This feature's coupling to the framework router, and through it to the runtime that executes mounts, is expressed only through the plain-argument registered-extensions source, the observable signal's transitions, and the back-projection helper's input, per domain — never through an injected port and never through an import of the runtime that owns occupancy or of the framework router.

**Registry grounding**: The registered-extensions source the framework router supplies for a domain (§1.5) has a natural origin this feature does not decree: the runtime's own registry of GTS-typed route-owner declarations. A route owner's own extension token is that declaration's own normalized route-identity value — which concrete field on a registration supplies it is the `mfes` package's own contract (`cpt-frontx-routing-adr-occupant-identity-stability`) — the derivation itself is the navigation substrate's own name-validity primitive (`cpt-frontx-algo-routing-navigation-substrate-name-validity`, Extension-token derivation), not redefined here. Uniqueness of a declared extension token among a domain's own registrations is the framework router's registration-time check (PRD §11; DESIGN §2.3, O3b). Which route a domain declares, at any depth, is likewise not decided by this feature: it is the domain's own declared route, admitted by the framework router only when no other routed domain live in the page already holds it (DESIGN §2.3, O1) — this feature only resolves against whatever domain key it was handed, never against how that route was chosen. That every child microfrontend runs its own registry, unreachable by enumeration from its own parent, is what makes a per-domain registered-extensions source a structural necessity rather than a convenience — no single registry could enumerate every domain's own occupants even if this feature wanted one to.

**Binding obligation**: Pursuing two-way agreement between the URL and what is actually mounted is not this package's obligation on its own, at any domain — it is the framework router's, built on this signal and this helper (PRD §11; `cpt-frontx-adr-extension-routing-port`, URL ownership). DESIGN §2.3 states each of the framework router's obligations normatively (O1, O3a, O3b, O5, O6, O7); the points below are how those obligations meet this feature's own surfaces, not a second normative copy. The obligation is recursive: the framework router carries it for every routed domain, with no lesser or different obligation for a domain several levels deep than for the outermost one, and no lesser or different obligation for a domain admitting several concurrent occupants than for one admitting a single occupant. For every routed domain, the framework router:
1. Creates the observer described in §3 (Observable Transition Signal) for that domain once the domain exists and its route has been admitted (DESIGN §2.3, O1), supplying that domain's own registered-extensions source and the domain's own declared route as its domain key.
2. On each notified transition, turns every difference between the entries the transition reports and what is mounted at that domain into `mount_ext` and `unmount_ext` action chains sent through the runtime's actions-chains mediator, each carrying the history intent `none`, because the URL already says what the mounts must become (DESIGN §2.3, O6): one `unmount_ext` for each occupant the diff reports removed and one `mount_ext` of the named route owner for each entry the diff reports added, each its own actions chain, removals dispatched before additions, uniformly in every domain. An owner change is an `unmount_ext` of the previous owner plus a `mount_ext` of the new one. A removal's failure holds back no addition. The domain's handler decides the outcome of every request, including a request that overlaps a mount or unmount of the same extension in flight; a request the handler refuses — an Exclusive domain's `unmount_ext` among them — leaves the mounts as they are, and the framework router pursues agreement. An entry the diff reports changed only in payload needs no chain: the already-mounted occupant's own router reads its updated payload from the shared history. Reordering alone implies no chain of its own. The framework router never mounts, unmounts, or reconciles directly off a transition. This feature resolves no mount race of its own — a chain driven by this signal races against, and is resolved by, exactly the same runtime mechanism any other chain already is.
3. Reflects into the URL each `mount_ext` or `unmount_ext` execution the runtime reports as settled in that domain, through the URL back-projection helper (§3, URL Back-Projection Helper Via Own-Key Rewrite), as one helper call per settled report (DESIGN §2.3, O5). Of the action it reads only the report — never the action type, and with no cardinality knowledge of the domain: the call's delta follows the extensions the report lists as mounted and unmounted, and a report listing nothing mounted and nothing unmounted produces no call. When the report lists as unmounted an extension whose zone hosts routed domains, the call's delta names, in `clearedDomainKeys`, the exact domain keys of the routed domains the framework router knows from its own orchestration to be nested in that departing extension's zone, so their entries leave in the parent action's own single write (DESIGN §2.3, O7); the nested releases inside that execution write and report nothing of their own. Unregistering an extension or a domain, and terminal disposal of a registry, are resource cleanup, not actions: they produce no helper call at all, and an entry they leave behind stays unresolved or inert (`cpt-frontx-adr-extension-routing-port`, Unregistration and disposal).
4. Sends no chain for the transition its own reflection produces, because that transition carries no difference. The helper's own history call dispatches the navigation substrate's fan-out exactly like any other navigation (`cpt-frontx-algo-routing-navigation-substrate-fanout-dispatch`), so the observer reports a transition resolving to the very entries the framework router just reflected. Those entries already agree with what is mounted at that domain, so point 2 finds no difference and yields no chain, and nothing is mounted twice or re-initialized. The framework router does not suppress the action effects of its own URL writes: wherever a transition carries a difference, point 2 turns it into chains, and an `unmount_ext` it sends for an extension already absent is handled by the domain like any other request.
5. Does not wait for a transition to conclude a domain has no occupant. Creating the observer against a domain key no entry currently carries reports an initial transition with an empty entry list and an empty diff (§3, Observable Transition Signal) — not the absence of a report — so a framework router that treats an empty entry list as "no occupant" from the moment it creates the observer needs no separate signal for that state.
6. Passes, as the helper's verb, the history intent the settled action's report carries: `push` for an action carrying `push` or no intent at all, `replace` for one carrying `replace`; an action carrying `none` produces no helper call at all, and every restoring chain of point 2 carries `none`, so restoring the mounts to a URL's state never writes history (DESIGN §2.3, O5). The helper accepts the verb as an explicit argument rather than fixing it itself (§3). The open-with-`push`, close-with-`replace` asymmetry — opening with `push` so a back step closes what was just opened, closing with `replace` so a back step after closing does not resurrect what was just dismissed, and a switch (the delta's `replaced` operation) opening with `push` so a back step returns to the entry it replaced — is the convention whichever party sends the action expresses through that action's own history intent (DESIGN §4, "A back-projection reflection and its chosen history verb"); the helper does not enforce it.
7. Applies the "same domain, same entries → no transition" rule within its own domain key only: a change to an entry under a foreign domain key, or to the hash, is not itself a transition, because resolution reads only the entries carrying this domain's own key.
8. Leaves a parent without rewriting the history entry the user is leaving. Because point 3 clears a departing extension's nested domains in the same single write as the parent's own change, no write ever strips the nested entries from the entry being left — neither before the parent's change nor after it. Under `push` — the verb of an opening action and of a switch — that entry survives intact in history, carrying the host's own entry and every nested occupant's own entry with that occupant's own parameters. A Back step lands on it, and a Forward step on the state after leaving; each is a restoring navigation, so point 2 brings the mounts to it — the host together with its nested occupants, each reading its own entry's own parameters — through chains carrying `none`, for which point 6 makes no helper call. This is the framework router's behaviour; what this package guarantees toward it is the helper's own: exactly one history write per call, clearing exactly the domain keys the call supplies (§3, URL Back-Projection Helper Via Own-Key Rewrite, Single-write note).

Further obligations apply once more than one domain, or more than one occupant per domain, is in play:
- A domain key with no observer currently reading it is inert — not an error, not a fallback state, and indistinguishable from a domain whose own wave has not yet reached it. Because point 3 clears the entries of a departing extension's nested domains in the parent action's own write, an inert entry is one no action removed — an entry a bookmark carries, or one unregistration or disposal left behind; an entry that does survive resolves correctly the moment a domain that reads it comes to exist, because every observer always reads the URL's current, live state, never a value captured earlier.
- Several domains wave independently: one domain's own transition and a sibling or nested domain's own transition carry no ordering guarantee relative to each other; when the framework router needs one to wait for the other, it coordinates that itself.
- Teardown of the occupant whose zone contains a nested domain — part of the parent action's own execution — releases that nested domain's observer, through the framework router, nested first, outermost last, or in whatever order the framework router already tears down the zone's own contents (DESIGN §2.3, O7). An observer left running past its own zone's teardown continues resolving and reporting against a domain key and a registered-extensions source whose owning zone no longer exists, reporting to a framework router that itself no longer has anything meaningful to do with the report.

Without the framework router carrying this obligation at every routed domain, the primitive, the signal, and the helper this feature publishes describe facts, not a pursued agreement — pursuing the two-way agreement is the framework router's obligation, built on this package's surfaces, not this package's alone.

**Multiplicity note**: More than one observer may exist in the same realm at once — one per routed domain, never more, regardless of how many occupants that domain's own occupancy strategy admits at once (`cpt-frontx-routing-fr-concurrent-occupant-projection`). A domain holding several concurrent occupants is resolved, observed, and back-projected by the identical one observer and one helper any domain uses; concurrency is a property of how many entries that domain's own ordered list carries, never a reason for a second observer. Each observer is independent, is created with its own registered-extensions source and its own domain key, tracks its own previously reported ordered entry list (§3, Observable Transition Signal), and is released independently (§3, Observer Release). All of them read the one navigation substrate's shared history and fan-out (`cpt-frontx-routing-principle-single-history-authority`), so every observer resolves against the same `location` a given round dispatches, but resolves it against its own domain's own registered extensions and its own domain key's own entries — which is exactly what makes resolving a deep URL a wave rather than one event (§1.1).

### 1.5 Contract Shapes

Field-level shapes for this feature's own inputs and outputs, per `cpt-frontx-adr-contract-schema-ownership` (owned contract role in DESIGN, decision rationale in the ADR, field-level schema in the owning FEATURE).

**Construction seam**: the observer (§3, Observable Transition Signal) and the URL back-projection helper (§3, URL Back-Projection Helper Via Own-Key Rewrite) are both obtained from a single factory bound to one navigation substrate `NavigationHistory` instance at once — never resolved by either one internally, and never defaulting silently to the realm-shared singleton behind a caller's back. Both read and write exclusively through the identical instance the factory was given, so a consumer testing against its own instance, or an SSR entry point supplying its own, gets the same read/write consistency an ordinary consumer bound to the realm-shared singleton gets. §3's own algorithm descriptions below state each half's behaviour against "the navigation substrate's shared history" generically; which concrete instance that is, is exactly what this factory's own binding fixes for both halves at once (DESIGN §3.3, `createRouteSignal`).

**Registered-extensions source** (supplied per domain by the framework router, passed as a plain argument — never an injected port):
- A readable snapshot of the current set of registered extension tokens for that one domain, in the same shape this feature's entry-resolution primitive reads; no extension token appears twice (PRD §11; DESIGN §2.3, O3b).
- Optionally, a way to observe a change to that set, since a domain's own registered-extensions set is not fixed for the realm's lifetime — a microfrontend can be registered or deregistered after the observer has already been created. A consumer whose set never changes after creation may supply a static snapshot with no change notification.
- Declares no cardinality floor: zero registered extensions is legal and simply means every entry under that domain key resolves to unresolved.

**Transition** (this feature's own output, delivered to the callback the consumer registers when creating one domain's own observer; never delivered at all when nothing about the ordered entry list or its resolutions changed):
- The domain key this transition concerns.
- **Entries**: the ordered list of every entry the current location carries under this domain key, in the order the grammar codec's own parse preserves — each carrying its own extension token and its own ordered payload params, and each flagged either resolved (a registered extension matches) or unresolved (none does).
- **Diff**, against the previously reported ordered list:
  - *Added* — extension tokens present now that were absent from the previous report.
  - *Removed* — extension tokens present in the previous report that are absent now.
  - *Payload-changed* — extension tokens present in both reports whose ordered payload params differ between them, with the extension token itself unchanged; a payload-only change never appears in *Added*, *Removed*, or as a cause of *Reordered* on its own (§9 of the URL grammar's own edge rules; DESIGN §1.1, Structural reset).
  - *Reordered* — whether the relative order of the extension tokens present in both reports changed, independent of whether any of them also carries a payload change.
  - *Resolution-changed* — extension tokens present in both reports, with the identical token and the identical ordered payload params, whose **resolution** differs between the two reports. The resolution is what Entries carry about an entry beyond its own token and payload — either "unresolved", or the route owner it resolved to — so this category covers both a change of resolved-versus-unresolved status (a registered-extensions-source change that newly matches, or newly stops matching, an entry's own token) and a change of the route owner itself while the entry stays resolved (a registration replaced under an unchanged token — a placeholder swapped for the real owner, a hot replacement). Route owners are compared by identity, never by value: a route owner is whatever the consumer registered and this feature states nowhere what one is made of, so a structural comparison would both invent a shape for it and report two separately created owners of identical content as the same owner — the very case a consumer needs told apart. Distinct from *Payload-changed*, which requires the payload itself to differ, and never overlapping with *Added*/*Removed*, since a *Resolution-changed* entry's own token is present in both reports.
  - *Unresolved* — the subset of Entries currently flagged unresolved, listed here so a consumer need not scan Entries to find them; not itself a diff category against the previous report, only a restated subset of the current Entries. An extension token moving into or out of this subset between two reports, with its own token and payload unchanged, is reported as *Resolution-changed* above.
  - A `replaced` back-projection write (§3, URL Back-Projection Helper) is not itself a sixth diff category: it is observed exactly as the old extension token appearing under *Removed* and the new extension token appearing under *Added*, both at the position the write assigned them — the diff stays agnostic to which back-projection operation produced the change it reports.
- No transition is delivered at all — not a further field value, an absence of delivery — when every one of the five diff categories above (*Added*, *Removed*, *Payload-changed*, *Reordered*, *Resolution-changed*) is empty or false relative to the previous report, regardless of whether the current Entries list itself is empty or non-empty; this is what a navigation that changes only a foreign domain key's own entries, or the hash, produces, since resolution reads only the entries carrying this domain's own key.

**Release function** (this feature's own output, returned to the consumer at observer creation, alongside registering its callback): a zero-argument function that, when called, unsubscribes the observer from everything it subscribed to — the navigation substrate's fan-out, and the registered-extensions source's own change notification when the source exposed one (§3, Observer Release). Calling it more than once is a no-op after the first call.

**URL back-projection — input**: the domain key whose own entries the caller wants reflected; a delta describing what changed, naming five kinds of change to this domain key's own entries, each keyed by extension token: an ordered list of entries to **add** (appended at the end of the full list); a list of extension tokens to **remove** (no gap left); a list of `{extension, params}` pairs whose payload changed **in place**, with the extension token itself unchanged — `params` is the entry's entire new ordered parameter list, replacing the one it already carries rather than merging into it (grammar §9 item 18); a caller wishing to keep a parameter that entry already had passes it again; a list of `{oldExtension, entry: {extension, params}}` pairs each **replacing** an existing entry's own extension token with a new entry at that same position; and, optionally, a **reordered** relative order for this domain's own currently-present entries, applied only within the set of positions those entries already occupy, leaving every other domain's own entries untouched. Alongside those five, the delta carries **`clearedDomainKeys`** — a list of domain keys naming exactly the nested routed domains the caller knows leave with an extension the delta removes or replaces; every entry under each named key is removed in the same history write as the rest of the delta (structural reset). The helper infers no domain key to clear from any key's shape or from a lexical prefix, and does not check that a named key belongs to the zone of a removed or replaced extension — it holds no record of which domains nest where (DESIGN §3.2, Route Ownership Signal, Responsibility boundaries). Together with the history verb the caller chooses, `push` or `replace` (§1.4, Binding obligation, point 6). The caller names only what changed; every entry under this domain key the delta does not name, and every entry under every other domain key `clearedDomainKeys` does not name, is left to the helper's own verbatim copy.

**URL back-projection — output**: one `push` or `replace` call, whichever verb the caller chose, against the shared history, that: writes this domain key's own ordered entry list with the delta's additions appended, the delta's removed extension tokens absent, the delta's payload changes applied in place at their existing position, each replaced extension token swapped for its new entry at that same position, and this domain's own entries reordered as given — within the positions they already occupied — when the delta names a reorder; removes every entry under each domain key `clearedDomainKeys` names — other than this domain key itself, whose own entries the delta alone governs — and no other entry; and copies every entry this domain key's own delta does not name, and every entry under any other domain key `clearedDomainKeys` does not name, verbatim in structure — the Escape-canonicalization note in §3 says what "verbatim" does and does not cover for an entry's own percent escapes. The helper reports nothing back to the caller beyond letting the underlying `push`/`replace` call either succeed or throw whatever the shared history itself throws, or throwing on its own for an input it rejects (§3, the validation of step 1.1, the replaced-presence check, the reorder permutation check, and the Collision note).

## 2. Actor Flows (CDSL)

### Deep Link Resolves Through The Route Ownership Signal, One Domain At A Time

- [ ] `p1` - **ID**: `cpt-frontx-flow-routing-route-ownership-signal-deep-link-cold-mount`

**Actor**: `cpt-frontx-routing-actor-framework-router`

**Use cases**: `cpt-frontx-routing-usecase-deep-link-to-microfrontend-screen`

**Success Scenarios**:
- A URL naming route owners several domains deep is opened cold, reloaded, or reached by back/forward while none of the extensions along that path are yet mounted; each domain's own observer, as it comes to exist, reports its entries appearing, the framework router turns each into a `mount_ext` chain carrying the history intent `none`, the runtime mounts each one, and once mounted its own engine provider reads the already-current location at start, so the mounted screen and the URL agree without a blank screen in between, at every domain — and no history write is made for any of it.
- A URL under a domain's own already-mounted entries is opened; that domain's own observer reports a `Payload-changed` and/or `Reordered` diff (or nothing, if neither changed) and the framework router sends no chain at that domain.

**Error Scenarios**:
- A domain's own entry carries an extension token no registration matches: that domain's own observer reports it as unresolved (an *Unresolved* entry in the transition, and an *Added* entry if it was not present in the previous report) and the framework router decides what that one entry shows; this feature takes no fallback action itself, and a domain several steps deeper that has not yet begun to exist is indistinguishable, at any shallower domain, from this same "nothing resolved" case.

**Steps**:
1. [x] - `p1` - The framework router creates the observer for a routed domain, passing that domain's own registered-extensions source together with the domain's own declared route as its domain key - `inst-create-observer`
   1. [x] - `p1` - The observer reads the current location, parses the entries via the grammar codec, and resolves every entry carrying this domain key through the entry resolution primitive (`cpt-frontx-algo-routing-route-ownership-signal-entry-resolution`) - `inst-resolve-entries-at-creation`
   2. [x] - `p1` - The observer reports an initial transition to the consumer's registered callback: the resolved ordered entry list, with every present extension token reported as `Added` (`cpt-frontx-algo-routing-route-ownership-signal-observe-change`) - `inst-report-initial-transition`
2. [x] - `p1` - **WHEN** the navigation substrate's fan-out subsequently notifies the observer of a back/forward step or any other navigation after creation (`cpt-frontx-algo-routing-navigation-substrate-fanout-dispatch`) - `inst-notify-navigation`
   1. [x] - `p1` - The observer re-resolves every entry currently carrying this domain key through the entry resolution primitive - `inst-resolve-entries`
   2. [x] - `p1` - The observer diffs the newly resolved ordered list against the previously reported one and reports the transition to the consumer's registered callback, or reports nothing if the diff is empty (`cpt-frontx-algo-routing-route-ownership-signal-observe-change`) - `inst-report-transition`
3. [ ] - `p1` - **FOR EACH** extension token the diff reports `Removed` - `inst-foreach-removed`
   1. [ ] - `p1` - The framework router sends one `unmount_ext` chain for that departing route owner through the runtime's actions-chains mediator, carrying the history intent `none`, in every domain, and dispatched before any `mount_ext` of the same transition (DESIGN §2.3, O6); the chain is its own actions chain, so its failure holds back no addition, and the domain's handler decides its outcome — a refused request, such as an Exclusive domain's `unmount_ext`, leaves the mounts as they are. The framework router never unmounts the route owner directly; this feature takes no unmounting action itself - `inst-router-sends-unmount-chain`
4. [ ] - `p1` - **FOR EACH** extension token the diff reports `Added` - `inst-foreach-added`
   1. [ ] - `p1` - The framework router sends a `mount_ext` chain for that route owner into the domain through the runtime's actions-chains mediator, carrying the history intent `none`, as its own actions chain dispatched after the transition's removals (step 3), and never mounts it directly off the transition (§1.4, Binding obligation, point 2; DESIGN §2.3, O6) - `inst-router-sends-mount-chain`
   2. [ ] - `p1` - Once the runtime has executed that chain and mounted the route owner, the microfrontend's own engine provider reads the current location from the shared history at start and reads its own entry's own payload, as specified by whichever engine-provider package implements the port - `inst-mfe-reads-location-at-start`
   3. [ ] - `p1` - **IF** the newly mounted route owner's own zone contains a further routed domain - `inst-if-nested-domain`
      1. [ ] - `p1` - Once that domain registers and the framework router admits its route (DESIGN §2.3, O1), the framework router creates that domain's own observer, supplying the domain's own declared route as its domain key and that domain's own registered extensions, repeating from step 1 at that domain - `inst-recurse-nested-domain`
5. [ ] - `p1` - **FOR EACH** extension token the diff reports `Payload-changed` - `inst-foreach-payload-changed`
   1. [ ] - `p1` - The framework router sends no chain; the already-mounted microfrontend reads its own entry's own updated payload through its own routing table - `inst-no-mount-action-payload`
6. [ ] - `p1` - **IF** the resolved ordered entry list carries an entry flagged unresolved - `inst-if-unresolved`
   1. [ ] - `p1` - The framework router decides what that one entry shows; this feature takes no fallback action itself - `inst-consumer-fallback`
7. [ ] - `p1` - **WHEN** the runtime reports a `mount_ext` or `unmount_ext` execution from steps 3 or 4 as settled - `inst-when-restoring-chain-settles`
   1. [ ] - `p1` - The framework router makes no back-projection call for it, because its report carries the history intent `none` the chain carried: the URL already carries the state the chain restored, so restoration writes no history (§1.4, Binding obligation, point 6; DESIGN §2.3, O5) - `inst-router-no-write-for-restoration`

**Postconditions**:
- Each domain's own mounted set and the entries it resolved agree, for every chain the domain's handler accepts, without a blank screen, because a freshly mounted router reads the already-current location rather than starting from a blank route, and because the framework router turned that domain's own reported transition into action chains the runtime executed — independently at every domain, with no event asserting that every domain resolved together, and with no history write made for any of it.

## 3. Processes / Business Logic (CDSL)

### Entry Resolution

- [x] `p2` - **ID**: `cpt-frontx-algo-routing-route-ownership-signal-entry-resolution`

**Input**: A domain key; the ordered list of entries the grammar codec's own parse produced (`cpt-frontx-algo-routing-navigation-substrate-grammar-parse`), each carrying its own `domainKey`, `extension`, and ordered `params`; that domain's own registered-extensions source, supplied by the caller as a plain argument.

**Output**: The ordered subsequence of the input entry list whose own `domainKey` equals the given one, each entry paired with a resolution: the route owner its `extension` names, when that token matches a registration in the given registered-extensions source, or "unresolved" when it matches none.

**Steps**:
1. [x] - `p1` - Filter the input entry list to the ordered subsequence whose own `domainKey` equals the given domain key, preserving the parse's own left-to-right order - `inst-filter-by-domain-key`
2. [x] - `p1` - **FOR EACH** entry in that subsequence, in order - `inst-foreach-filtered-entry`
   1. [x] - `p1` - **IF** the entry's own `extension` matches an extension token in the given registered-extensions source, using the navigation substrate's own name-equality predicate (`cpt-frontx-algo-routing-navigation-substrate-name-validity`) - `inst-if-extension-matches`
      1. [x] - `p1` - Pair the entry with the matching registration's own route owner - `inst-pair-resolved`
   2. [x] - `p1` - **ELSE** no registration matches - `inst-else-no-match`
      1. [x] - `p1` - Pair the entry with "unresolved" - `inst-pair-unresolved`
3. [x] - `p1` - **RETURN** the ordered list of `{entry, resolution}` pairs - `inst-return-resolution`

**Rationale**: This algorithm is a thin filter-and-match over the substrate's own grammar codec and name-equality predicate, called once per domain; it defines no parsing or matching rule of its own, so a change to either — the codec's own parse rules, or the name-equality comparison — is a change to the navigation substrate's own algorithms alone (`cpt-frontx-feature-routing-navigation-substrate` §3), never to this one. Resolving to "unresolved" rather than dropping an unmatched entry is what lets a domain's own consumer report a fallback for it, and what lets a later registration change resolve it without the entry ever having left the URL (§1.1; DESIGN §1.1, Structural reset).

### Observable Transition Signal

- [x] `p2` - **ID**: `cpt-frontx-algo-routing-route-ownership-signal-observe-change`

**Input**: A domain's own registered-extensions source, passed as a plain argument at creation (never an injected port); that domain's own key — its declared route, a single `name` — passed at that same moment; a callback the consumer registers to receive a transition; the navigation substrate's shared history and its fan-out subscription; the observer's own internally tracked previously reported ordered entry list, updated after every resolution this algorithm performs.

**Output**: An observer subscribed to the navigation substrate's fan-out, plus a release function returned to the consumer at creation (`cpt-frontx-algo-routing-route-ownership-signal-release`); on creation, and on every subsequent navigation that changes something about this domain key's own entries, one call to the consumer's callback carrying a transition (§1.5, Transition); no call at all when nothing did.

**Steps**:
1. [x] - `p1` - **WHEN** the consumer creates the observer, passing that domain's own registered-extensions source and that domain's own key, and registering its callback - `inst-when-create`
   1. [x] - `p1` - Validate the given domain key against the navigation substrate's own `domain-key` production — a single `name`, checked with the name-validity check (`cpt-frontx-algo-routing-navigation-substrate-name-validity`, Validity), so a key carrying `.` or any other character outside the `name` alphabet fails it — and validate every extension token the given registered-extensions source declares against the name-validity check alone (`cpt-frontx-algo-routing-navigation-substrate-name-validity`) — synchronously, before any resolution runs — and **THROW** a clear error naming the first offending value if any fails; only once this validation passes, read the current location, parse it via the grammar codec, resolve the entries carrying this domain key through the entry resolution primitive (`cpt-frontx-algo-routing-route-ownership-signal-entry-resolution`), and record the just-resolved ordered entry list as the observer's previously reported state - `inst-initial-resolve`
   2. [x] - `p1` - Subscribe to the navigation substrate's fan-out (`cpt-frontx-algo-routing-navigation-substrate-fanout-dispatch`) — **before** reporting the initial transition below, not after — so that a synchronous re-navigation the consumer's own first callback performs (step 1.3, below) is caught by this same subscription rather than missed entirely, exactly as any later navigation would be. Step 1.1's own baseline is already recorded by this point, so a reentrant dispatch this subscription catches during step 1.3 has a correct previously-reported state to diff against - `inst-subscribe-fanout`
   3. [x] - `p1` - Report an initial transition whose Entries are the just-resolved ordered list and whose diff reports every present extension token as `Added` (and as `Unresolved` too, for any entry paired with "unresolved") — **IF** this call throws, release the subscription registered in step 1.2 before propagating the throw: this step runs after that subscription already exists, so a throw here must not leave it registered with no release function ever reaching the caller, since one is only returned by step 1.5 below, which a throw here prevents from being reached at all - `inst-initial-report`
   4. [x] - `p1` - **IF** the registered-extensions source exposes a change notification (§1.5) - `inst-if-source-has-notification`
      1. [x] - `p1` - Subscribe to it as well - `inst-subscribe-extensions-source`
   5. [x] - `p1` - **RETURN** the release function (`cpt-frontx-algo-routing-route-ownership-signal-release`) to the consumer, closed over the subscription(s) registered in steps 1.2 and 1.4 - `inst-return-release`
2. [x] - `p1` - **WHEN** the navigation substrate's fan-out notifies the observer of a navigation - `inst-when-navigation`
   1. [x] - `p1` - Read the current location, parse it via the grammar codec, and resolve the entries currently carrying this domain key through the entry resolution primitive, reading the consumer's own registered-extensions source at this same moment - `inst-resolve-current`
   2. [x] - `p1` - Compute the diff between the newly resolved ordered list and the previously reported one: extension tokens present now but not before are `Added`; present before but not now are `Removed`; present in both with different ordered payload params are `Payload-changed`; whether the relative order of tokens present in both changed at all is `Reordered`; present in both with the identical payload params but a resolution that differs from the previous report — either the resolved-versus-unresolved status itself, or, for an entry resolved in both, the route owner it resolves to, compared by identity (§1.5, *Resolution-changed*) — are `Resolution-changed`; entries currently paired with "unresolved" are also listed under `Unresolved`, restating a subset of the just-resolved Entries rather than computing a sixth diff category - `inst-compute-diff`
   3. [x] - `p1` - **IF** every one of `Added`, `Removed`, `Payload-changed`, `Reordered`, and `Resolution-changed` is empty or false — regardless of whether the just-resolved Entries list itself is empty or non-empty - `inst-if-diff-empty`
      1. [x] - `p1` - Report no transition — nothing about this domain key's own entries changed; this is, in particular, what a navigation that changes only a foreign domain key's own entries, or the hash, produces, since resolution reads only the entries carrying this domain's own key. Record the newly resolved ordered entry list as the observer's new previously reported state, immediately — there is no consumer callback in this branch that could fail to finish processing it - `inst-no-report-unchanged`
   4. [x] - `p1` - **ELSE** - `inst-else-diff-nonempty`
      1. [x] - `p1` - Report a transition carrying the newly resolved Entries and the computed diff - `inst-report-transition`
      2. [x] - `p1` - Record the newly resolved ordered entry list as the observer's new previously reported state — **only once step 2.4.1's own report call returns without throwing**: a consumer callback that throws while processing a transition has not finished processing it, so the baseline must stay exactly where it was, at the previously reported state, rather than silently advancing past a transition the consumer never actually handled. The practical effect: the next navigation that returns to the identical resolved state recomputes the identical, non-empty diff against that same unmoved baseline and reports it again, instead of diffing against a state the throwing callback never actually saw take effect and finding nothing to report - `inst-record-navigation-state`
3. [x] - `p1` - **WHEN** the registered-extensions source's own change notification fires, for a source that exposes one (§1.5) - `inst-when-extensions-source-changes`
   1. [x] - `p1` - Validate every extension token the source's now-current set declares against the navigation substrate's own name-validity check (`cpt-frontx-algo-routing-navigation-substrate-name-validity`) — synchronously, before any re-resolution runs — and **THROW** the same clear error naming the first offending value that observer creation would throw, if any fails - `inst-validate-extensions-source-change`
   2. [x] - `p1` - Re-run steps 2.1 through 2.4 against the current entries and the source's now-current registered extensions, exactly as if a navigation had occurred — a registration or deregistration can change which entries resolve, or which entries are unresolved, without the URL itself moving. A consumer callback that throws during this re-run is isolated from the registered-extensions source's own change-notification emitter, exactly as a fan-out subscriber's own throw is isolated from the navigation substrate's fan-out (`cpt-frontx-algo-routing-navigation-substrate-fanout-dispatch`): the throw does not reach that emitter, so it never stops the source from notifying any other listener it has, and the observer's own baseline still does not advance past the transition the callback never finished processing (step 2.4.2). The validation throw in step 3.1 above is not isolated this way — it is this observer's own input-validation failure, not a consumer callback's, and must still reach whichever code triggered the change - `inst-reresolve-on-source-change`

**Key-mismatch note**: A domain's own key is fixed at this observer's own creation and neither step 1 nor step 2 ever updates it in place. If no entry in the current location carries that key at all, steps 1.1 and 2.1 resolve an empty ordered list — not a fault condition, but the ordinary outcome for a domain key nothing currently addresses, reported (or diffed) exactly like any other resolution. A domain's key is its own declared route, declared once at that domain's registration (PRD §1.4, Glossary, domain key), so this algorithm has no mechanism, and no need for one, to replace the key of an observer still running.

**Re-entrancy note**: A navigation, or a registered-extensions-source change, that a consumer's own `onTransition` callback triggers synchronously from inside a transition it is already receiving — on either trigger axis this algorithm serves, step 2 or step 3 — is deferred to its own later run of steps 2.1-2.4 rather than folded into, or run nested inside, the one already in progress, mirroring the navigation substrate's own fan-out deferral of a reentrant navigation (`cpt-frontx-algo-routing-navigation-substrate-fanout-dispatch`). Without this, a nested run's own commit of the previously-reported state (step 2.4.2) is overwritten the instant the outer run resumes and performs its own, by-then-stale commit: the previously-reported state would permanently disagree with the current location, and the next navigation back to that exact state would diff against it as empty and report nothing at all — silently, and forever, rather than merely late. The navigation substrate's own fan-out only defers a reentrant navigation triggered from inside another navigation's own fan-out round; this algorithm's own deferral additionally covers a reentrant trigger crossing from the registered-extensions-source axis (step 3) into a navigation, and a reentrant registered-extensions-source change triggered from inside a fan-out report, since the fan-out's own deferral does not reach either. When more than one reentrant trigger queues while a run is already in progress, each deferred run still gets its own turn: a consumer callback that throws during one deferred run is isolated from that turn onward exactly as step 2.4.1's own throw already is at the outermost run — it does not stop a run still queued behind it from running in its own later turn, and it does not reach the navigation substrate's fan-out or the registered-extensions source's own change-notification emitter either. It leaves only that one deferred run's own baseline commit (step 2.4.2) un-advanced, at whatever state was previously reported before that turn began. A callback's throw during a deferred run is reported rather than merely swallowed, on the same terms the navigation substrate's own fan-out reports one (`cpt-frontx-algo-routing-navigation-substrate-fanout-dispatch`, step 4.2.1.2.2): isolation is what the runs still queued are owed, but a callback failing on every run must not be indistinguishable from one succeeding. Deferral is also bounded, by the identical rule and the identical bound the substrate's own fan-out applies to its queue (that algorithm's step 4.4.2): a callback that triggers a fresh run from every run it receives — most readily by mutating the registered-extensions source from inside the transition that source's own change produced — would otherwise be served forever, and because deferred runs are drained in a loop rather than nested inside one another, nothing about that would ever surface on its own. Past the bound, whatever is still queued is abandoned and a clear error naming the bound is thrown, reaching the trigger axis that fed the loop exactly as any other failure raised there would.

**Rationale**: Reporting the whole ordered entry list, not only what changed, is what lets a consumer render a domain's own current occupancy directly from one transition without reconstructing it from a sequence of diffs; carrying the diff alongside it is what lets that same consumer act only on what actually changed, at whatever occupant count the domain admits (`cpt-frontx-routing-fr-concurrent-occupant-projection`). Separating `Payload-changed` from `Added`/`Removed` is what keeps a domain from double-mounting an occupant whose parameters merely moved — the very case the URL grammar's own structural-reset rule treats as leaving every nested domain's own entries untouched (§9 of the URL grammar; DESIGN §1.1, Structural reset) — and separating `Reordered` from both is what lets a domain that assigns meaning to entry order (a stack of sheets, a widget layout) react to a pure reorder without mistaking it for an occupancy change. Separating `Resolution-changed` from all three is what keeps a registration-set change that leaves an entry's own token and payload untouched — a route owner registering or deregistering — from going unreported entirely: without its own diff category, an entry moving between resolved and unresolved with nothing else about it changing would satisfy none of `Added`/`Removed`/`Payload-changed`/`Reordered`, and this observer would silently fire no transition on every such fan-out round even though a consumer showing a fallback for that one entry needs to know. Defining that category over the whole resolution, rather than over the resolved-versus-unresolved status alone, closes the identical hole one step in: a registration replaced under an unchanged extension token leaves the status untouched while changing the only other thing Entries carry about that entry, so a status-only comparison reported nothing at all and the consumer kept the route owner it already held for as long as the observer lived — there is no other report it could have learned the new one from, since a transition is delivered only when the diff is non-empty. Filtering out an empty diff is the one case this algorithm treats as not worth reporting: nothing about this domain's own occupancy, payload, order, or resolution status could have changed when every diff category is empty. Reporting an initial transition at creation, rather than only from the first subsequent navigation, is what covers a cold load or a reload — the very case a consumer most needs this signal for — from the first moment the observer exists, even when that initial transition's own Entries list is empty.

### Observer Release

- [x] `p2` - **ID**: `cpt-frontx-algo-routing-route-ownership-signal-release`

**Input**: An observer created by `cpt-frontx-algo-routing-route-ownership-signal-observe-change`, at whichever domain it was created for, and the internal subscription(s) it registered at creation: the navigation substrate's fan-out, and the registered-extensions source's own change notification, when the source exposed one.

**Output**: Every subscription this observer itself registered, unsubscribed; the observer reports no further transitions after this point, including a transition from a fan-out round already in progress at the moment release was called (Round-in-progress note, below), and including a round this observer had already queued for itself on either trigger axis before release was called (Queued-round note, below).

**Steps**:
1. [x] - `p1` - **WHEN** the consumer calls the release function returned at observer creation - `inst-when-release-called`
   1. [x] - `p1` - Unsubscribe from the navigation substrate's fan-out subscription registered at observer creation - `inst-unsubscribe-fanout`
   2. [x] - `p1` - **IF** the observer also subscribed to the registered-extensions source's own change notification at creation - `inst-if-subscribed-extensions-source`
      1. [x] - `p1` - Unsubscribe from that subscription as well - `inst-unsubscribe-extensions-source`
   3. [x] - `p1` - **IF** the release function is called again after the first call - `inst-if-called-again`
      1. [x] - `p1` - Treat the call as a no-op — nothing is subscribed to unsubscribe from a second time - `inst-release-idempotent`
2. [x] - `p1` - **RETURN** - `inst-return-release-done`

**Round-in-progress note**: The navigation substrate's own fan-out dispatch fixes a round's composition from a snapshot taken when the round starts, but always skips a callback no longer present in the live subscriber registry by the time the round's own iteration reaches its slot (`cpt-frontx-algo-routing-navigation-substrate-fanout-dispatch`) — a callback's own release always wins over a still-pending, not-yet-invoked slot a round's snapshot reserved for it. Calling this observer's own release function removes its callback from that live registry immediately (step 1.1), so if a fan-out round is already in progress at that moment and this observer's own callback is part of that round's snapshot but has not yet been invoked, that pending invocation is skipped, not delivered. An invocation of this observer's callback that already completed earlier in the same round, before release was called, is not undone.

**Queued-round note**: Separately from the fan-out dispatch's own snapshot, this observer's own reentrancy guard (`cpt-frontx-algo-routing-route-ownership-signal-observe-change`, §3) can leave one of its own rounds queued rather than run immediately, when a consumer callback triggers a reentrant transition on either trigger axis while a round is already running — this is what happens on the registered-extensions-source axis in particular, since the fan-out axis's own nesting is already deferred one level up by the fan-out dispatcher itself. This queue obeys the identical release rule as the fan-out dispatcher's own snapshot: release always wins over a round still queued, not only over a round the fan-out dispatcher itself has not yet delivered. Concretely — after release returns, none of this observer's own queued rounds run, whether release was called from outside every callback or from inside one; a release performed from inside a callback that runs while a round is queued behind it takes effect immediately, stopping every round still queued behind that callback, not only rounds triggered afterward; and a callback that throws while other rounds remain queued behind it does not, on its own, abandon those still-queued rounds for an observer that release has not been called on — only release itself stops them, isolation from a throw is unrelated to that.

**Rationale**: This feature holds no lifecycle notion of its own beyond the subscriptions its own observer registers (§4, No Feature-Owned State Machine), so leaking one is entirely this algorithm's own responsibility to prevent. Releasing both subscriptions this observer itself registered — not only the fan-out one — is what DESIGN §4 already names this feature as the owner of preventing: an observer whose registered-extensions-source subscription outlives it leaks exactly as durably as one whose fan-out subscription does, at whichever domain it was created for. Unsubscribing from the fan-out immediately, in step 1.1, rather than deferring it to some later point, is what makes the Round-in-progress note's guarantee hold: release only ever prevents an invocation still pending in a round already in progress, it never needs to retract one already delivered.

### URL Back-Projection Helper Via Own-Key Rewrite

- [x] `p2` - **ID**: `cpt-frontx-algo-routing-route-ownership-signal-url-back-projection`

**Input**: A domain key; a delta — an ordered list of entries (`{extension, params}`) to add; a list of extension tokens to remove; a list of `{extension, params}` pairs whose payload changed in place with the extension unchanged; a list of `{oldExtension, entry: {extension, params}}` pairs each replacing an existing entry's own extension token with a new entry at that same position; and, optionally, a new relative order for this domain's own currently-present entries, applied only within the positions those entries already occupy; and `clearedDomainKeys`, a list of the nested routed domains' keys whose entries leave in this same write (§1.5, URL back-projection — input); the history verb the caller chooses, `push` or `replace` (§1.4, Binding obligation, point 6); and, optionally, a page hash to write — a value distinct from every domain key's own entries and never itself an entry, governing only which page hash the same single write carries.

**Output**: One `push` or `replace` call, whichever verb the caller supplied, against the shared history, that mutates only this domain key's own entries and removes only the entries under the domain keys `clearedDomainKeys` names, leaving every other entry in the URL exactly as it was, and that carries the caller's given page hash when one was given (an empty string clears the hash) or the URL's own current page hash, preserved verbatim, when none was given.

**Steps**:
1. [x] - `p1` - A caller calls this helper with the domain key, the delta, the chosen verb, and, optionally, a page hash to write — the framework router, to reflect one `mount_ext` or `unmount_ext` execution the runtime reported as settled in that domain and carrying a history intent other than `none` (§1.4, Binding obligation, points 3 and 6), or an occupant's own engine provider, to write that occupant's own entry's own parameters as a payload change (§1.1) - `inst-consumer-calls-helper`
   1. [x] - `p1` - Validate the given domain key, and every domain key the delta's `clearedDomainKeys` names, against the navigation substrate's own `domain-key` production — a single `name`, checked with the name-validity check (`cpt-frontx-algo-routing-navigation-substrate-name-validity`, Validity) — and validate every extension token named anywhere in the delta (its added list, its removed list, its payload-changed list, the old and new extension of every replaced pair, and its reordered list, when given) against the name-validity check alone — synchronously, before any parsing runs — and **THROW** a clear error naming the first offending value if any fails - `inst-validate-back-projection-tokens`
2. [x] - `p1` - Read the current location and parse it via the grammar codec (`cpt-frontx-algo-routing-navigation-substrate-grammar-parse`), preserving the full parsed entry list of every domain key, not only the given one - `inst-parse-current`
3. [x] - `p1` - Compose this domain key's own new ordered entry list, preserving position: keep every currently parsed entry under this domain key whose own extension is named by neither the delta's removed list nor, as an old extension, the delta's replaced list, in its existing position; apply the delta's payload-changed pairs to the matching entries in place, at their existing position, by replacing each matching entry's own parameter list wholesale with the pair's own `params` — never merging it with the parameter list that entry already carried; replace, at its existing position, each entry the delta's replaced list names by its old extension token with the delta's given new entry for that pair; **IF** the delta names a reorder for this domain, reassign the entries surviving the steps above to the identical set of positions they already occupy among this domain's own entries, in the given new relative order, touching no other domain's own entries; append the delta's added entries, in the order the caller supplied them, at the end - `inst-compose-own-entries`
   1. [x] - `p1` - **IF** the delta names a replacement whose `oldExtension` is carried by no entry currently under this domain key, **THROW** a clear error naming the domain key and that old extension token, writing nothing — neither this domain key's own rewrite nor the removal of any entry under the delta's `clearedDomainKeys`. A replacement stands its new entry at the old entry's *own position*, and an absent token has no position, so the operation the pair names cannot be performed at all; appending the new entry at the end of the full list instead would silently demote the pair to an addition and produce exactly the entry order `replaced` exists to stop producing. Checked before the reorder permutation check below, so a delta getting both wrong is refused on the cause the reorder's own surviving set is derived from. The error names the domain key and the missing token because that is what a consumer acts on: re-read the live entry list, recompute the delta against it, and call again naming the operation that list admits - `inst-replaced-old-extension-present-check`
   2. [x] - `p1` - **IF** the delta names a reorder, read each surviving entry by the extension token it carries in the *currently parsed* location, never by a token the same delta introduces: an entry the delta replaces is named by its `oldExtension`, since `reordered` orders positions and never also renames what stands in them, and an entry the delta adds is never named at all, since additions land after this step, at the end of the full list (step 5), outside the positions a reorder may touch. **IF** the given order is not exactly a permutation of that surviving set — a survivor missing from it, a token outside it, or a token named twice — **THROW** a clear error naming the domain key and the given order, writing nothing: a short order would silently drop a survivor the caller never asked to remove, and a repeated token would silently stand the identical entry at two positions, both of which reach the URL as a change the caller did not ask for and cannot see in its own delta - `inst-reordered-permutation-check`
4. [x] - `p1` - **FOR EACH** domain key the delta's `clearedDomainKeys` names - `inst-foreach-cleared-domain-key`
   1. [x] - `p1` - Remove every entry in the currently parsed entry list whose own `domainKey` equals that key — unless that key is this domain key itself, whose own entries step 3 alone governs — in the same history write as step 7: exactly the named key, never a key inferred from any key's shape, from a lexical prefix, or from the delta's removed or replaced tokens; a named key no entry carries removes nothing (structural reset, `cpt-frontx-routing-adr-domain-occupancy-addressing-granularity`) - `inst-clear-nested-domain-entries`

8. [x] - `p1` - **RETURN** - `inst-return-reflected`

**Collision note**: A delta may name an extension token this domain key already carries, or name one twice within itself — an `added` entry whose token an entry under this domain key already holds, an `added` list carrying one token twice, or a `replaced` pair whose new entry's token another entry under this domain key already holds. None of these is a position this helper can compose: two entries sharing one domain key and one extension token are not a URL this grammar can express, which is exactly why the codec refuses to serialize such a list (`cpt-frontx-algo-routing-navigation-substrate-grammar-serialize`, step 2.4). Step 6 therefore **THROWS** that same duplicate-extension error, naming the two colliding entries, and step 7 never runs — the location is left exactly as it was. Unlike the validation of step 1.1, this failure cannot be raised before the parse: whether an added token collides is a fact about the *current* URL, not about the delta alone. A caller reopening an entry under a token already present expresses it as a payload change, or as a removal and an addition in the one delta — the removal clears the token's own position first, so the addition at the end of the list collides with nothing.

**Single-write note**: Each call issues exactly one history write, and that one write both applies the delta to this domain key's own entries and removes the entries under exactly the domain keys `clearedDomainKeys` names; no part of a call — the clearing included — is ever issued as a write of its own, before or after. A call never touches a history entry other than the one its own verb writes — the new entry under `push`, the current one under `replace` — so the entry a `push` leaves behind keeps every entry it carried, the nested domains' entries included. This is the whole of this package's part in leaving a parent: it decides neither which keys to clear nor when to call. That a Back step afterward brings the host back together with its nested occupants' own entry parameters, and that the chains restoring them write nothing, is the framework router's behaviour built on this one write (§1.4, Binding obligation, point 8).

**No-op note**: This helper writes on every call. A delta naming no change at all — an empty delta, or one whose every named token is absent — still composes the current entry list and still issues exactly one `push` or `replace` of the result, so two consecutive empty deltas produce two identical history calls and, under `push`, two indistinguishable history entries. No comparison against the current URL suppresses the write, because an empty delta is also how a caller writes a page hash and nothing else (step 1's optional page hash is a first-class input, not a rider on a non-empty delta), and because a caller that wants a back step to return to the state it is leaving is entitled to ask for one. Deciding whether anything actually changed belongs to the caller, which already knows — §1.4's Binding obligation has the framework router call this helper only to reflect a settled action, and never for one carrying the history intent `none`. The same applies to a removed or payload-changed token this domain key does not currently carry, and to a `clearedDomainKeys` key no entry carries: that name matches no entry and changes nothing, and the call still writes. A `replaced` pair whose `oldExtension` this domain key does not currently carry is **NOT** among those tolerated cases and never reaches this note: unlike a removal, whose postcondition — that token absent — already holds, and unlike a payload change, which is inert with no entry to rewrite, a replacement has an effect of its own that an absent position makes impossible to deliver, so step 3.1 refuses it and writes nothing.

**Escape-canonicalization note**: "Verbatim", for every entry this delta does not name, means its structure — its domain key, its extension token, and its ordered parameter list, each preserving what it decoded to — not its original bytes. Step 2 parses the whole location and step 6 re-serializes it, so every entry in the URL, including every entry under another domain key, comes back in the codec's own canonical encoding: a percent escape covering a character the encoder does not escape is written out as that character (`?other=x;q=%41` returns as `?other=x;q=A`), while an escape the encoder does need keeps its escaped form (`;q=a%20b` returns unchanged). What survives byte for byte is the foreign *segment* — a query segment that never parsed as an entry of this grammar at all (an OAuth `code`, an analytics `utm_*`), which the codec carries through as raw text and re-emits after the entries. A consumer that needs a byte-exact value from another party's query must therefore keep it in a foreign segment, not in an entry under a domain key of this grammar.

**Timing note**: This helper's guarantee — that a call issued eagerly still lands on the browser's own current, post-move entry list — holds for a user's own back/forward step, and for a third-party history move that has already completed by the time this helper is called: in both cases the browser's own location has already settled to its post-move value before any of this library's own code runs, even though this library's own notification of that move still lags asynchronously behind it (`cpt-frontx-algo-routing-navigation-substrate-fanout-dispatch`). It does not hold for a `go` call issued through this same navigation-substrate instance: unlike a user's own gesture or an already-completed third-party move, this instance's own `go` call does not complete synchronously at its own call site — the browser processes the move, and raises the event this library's fan-out observes, only afterward. Calling this helper in the window between this instance's own `go` call and the fan-out's own notification of the move that call produced is therefore not a supported use. A caller that wants to write after issuing its own `go` call instead waits for the transition that call produces (§3, Observable Transition Signal) before calling this helper.

**Rationale**: Reading and re-serializing the full currently parsed entry list, rather than mutating a fragment of the raw URL string directly, is what lets this helper touch only the domain key it was asked to change plus the entries under the nested domain keys the caller named — every other domain key's own entries pass through step 5 unexamined and unchanged, satisfying the Control boundary (DESIGN §1.1) that keeps this helper from ever reading or editing another domain's own part of the URL beyond the one narrow exception structural reset requires. Taking the nested domain keys from the caller rather than deriving them is what the grammar itself requires: a domain key is the domain's own declared route, a single `name` carrying no ancestry, so nothing about a key's shape says which extension's zone it sits in — only the framework router's own orchestration knows which domains leave with a departing extension (DESIGN §2.3, O7). Clearing them in the same single write as the parent's own change, never in a write of their own, is what keeps the history entry being left intact: no write ever strips a nested domain's entries from that entry, so a Back step can return to the host together with its nested occupants' own parameters (§1.4, Binding obligation, point 8). A payload-only change or a pure reorder of a parent entry leaves every nested entry untouched, because the caller names no nested key for either — nothing about which extension occupies that entry changed (§9 of the URL grammar; DESIGN §1.1, Structural reset). Giving `replaced` its own operation, rather than expressing a switch as a `removed` plus an `added`, is what keeps the new entry at the old entry's own position instead of at the end of the full list; `reordered` needs its own operation for the identical reason, since a domain's own entries taking a new relative order among themselves is not expressible as any combination of the other four without also implying an add, a remove, or a position at the end that was never asked for. Leaving the choice of `push` versus `replace` to the caller, rather than fixing one verb for every call, is what lets the same helper serve both an opening reflection — where a `push` lets a later back step undo exactly what was just opened — and a closing reflection — where a `replace` avoids resurrecting a dismissed entry on a later back step — without this algorithm needing two names for what is otherwise one identical composition (§1.4, Binding obligation, point 6).

## 4. States (CDSL)

### No Feature-Owned State Machine

Not applicable. This feature holds no occupancy or binding lifecycle of its own to model as named states with guarded transitions — an observer's own lifecycle is only "subscribed" or "released" (§3, Observer Release), a lifetime, not an occupancy state machine, at any domain. Occupancy, cardinality, and any state machine tracking which route owner currently occupies a domain belong entirely to the runtime that executes the framework router's action chains — the `mfes` runtime's own mount strategies and registry (`cpt-frontx-adr-extension-domain-occupancy`). Modeling that lifecycle here would duplicate a domain this package does not own and must stay agnostic of (`cpt-frontx-routing-principle-publishes-not-orchestrates`), so no state machine is defined for this feature.

## 6. Acceptance Criteria

- [x] Given every entry currently carrying one domain key and that domain's own set of registered extensions, entry resolution names each entry's own matching route owner or reports it unresolved, using the navigation substrate's own name-equality predicate and never re-implementing it.
- [x] A consumer creates the observer per domain by passing that domain's own registered-extensions source as a plain argument, never through an injected port, together with the domain key it was handed.
- [x] On creation, the observer resolves and reports the current ordered entry list for its own domain key before any subsequent navigation occurs, so a cold load or reload is covered from the observer's first moment, not only from the first navigation after it — including when that initial list is empty.
- [x] An observer subscribes to the navigation substrate's fan-out *before* it reports its own initial transition: a consumer whose very first callback navigates synchronously — the deep-link → mount → redirect pattern — has that navigation's own resulting transition delivered exactly once, not lost.
- [x] A consumer callback (`onTransition`) that throws does not advance the observer's own baseline: the next navigation to the identical resolved state re-delivers the identical transition rather than silently producing an empty diff — and therefore no report at all — forever after. The throw is still isolated from every other subscriber sharing the same fan-out round, exactly as any other subscriber's own throw is.
- [x] A consumer callback that throws on the very first, initial report leaves zero live subscriptions on the navigation substrate's fan-out — the subscription registered ahead of that first report (step 1.2) is released before the throw propagates out of observer creation, so a caller that catches the throw and does nothing further is not left with a stale registration that keeps invoking that same callback on every later navigation.
- [x] On every subsequent navigation that changes something about a domain key's own entries, the observer reports exactly one transition carrying the full ordered entry list and a diff: extension tokens newly present are `Added`, extension tokens no longer present are `Removed`, an extension token present both before and after with different payload params is `Payload-changed`, a change to the relative order of persisting tokens is `Reordered`, an extension token present both before and after with the identical payload params but a resolution that differs — its resolved-versus-unresolved status, or the route owner it resolves to — is `Resolution-changed`, and an entry whose own extension token matches no registration is listed under `Unresolved`, a restated subset of Entries rather than a sixth diff category.
- [x] No transition is reported when every one of `Added`, `Removed`, `Payload-changed`, `Reordered`, and `Resolution-changed` is empty, regardless of whether the current Entries list itself is empty or non-empty — including a navigation that changes only a foreign domain key's own entries or the hash, because resolution reads only the entries carrying this domain's own key.
- [x] **Resolution-changed scenario**: a `widgets` domain's own registered extensions stop including `chart-old` after having included it; the entry `widgets=chart-old;range=90d` carries the identical token and the identical payload across both reports, but its resolution status flips from resolved to unresolved. The domain's own observer reports a transition whose diff carries `Resolution-changed: [chart-old]` and empty `Added`/`Removed`/`Payload-changed`/`Reordered`.
- [x] **Route-owner swap scenario**: a `widgets` domain's own registered extensions keep declaring `chart`, but the route owner declared under that token is replaced by a different one; the entry `widgets=chart;range=90d` carries the identical token, the identical payload, and the resolved status across both reports. The domain's own observer reports a transition whose diff carries `Resolution-changed: [chart]`, and whose Entries carry the new route owner — rather than reporting nothing and leaving the consumer holding the previous owner for the rest of the observer's life.
- [x] A consumer callback that triggers a further resolve from every resolve it receives — by navigating, or by mutating the registered-extensions source from inside the transition that source's own change produced — does not run forever: after a fixed number of consecutive deferred runs the queue is abandoned and an error naming that bound is raised on the trigger axis that fed it. A callback that throws during a deferred run has that throw reported rather than discarded, while the runs still queued behind it keep their own turns.
- [ ] A payload-only change to an entry is reported as `Payload-changed` alone, never as `Added`/`Removed`; the framework router names no domain key to clear for it, so no nested domain's entries leave with it.
- [x] A change to the registered-extensions source's own declared set re-triggers resolution against the current entries, exactly as a navigation would, when the source exposes a change notification. A consumer callback that throws while processing that re-triggered transition is isolated from the registered-extensions source's own change-notification emitter, exactly as a fan-out subscriber's own throw is isolated from the navigation substrate's fan-out — one observer's own callback failure never stops the source from notifying any other listener it has. A navigation, or a further source change, that callback triggers synchronously does not overwrite the observer's own previously-reported state with a stale value: it is deferred to its own later resolve rather than run nested inside the report already in progress (Re-entrancy note, §3).
- [x] Creating an observer returns a release function; calling it unsubscribes the observer from the navigation substrate's fan-out and, when the registered-extensions source exposed one, from that source's own change notification, and the observer reports no further transitions afterward — including skipping a still-pending, not-yet-invoked delivery from a fan-out round already in progress at the moment release was called, without undoing one the round already delivered earlier. Calling it again is a no-op.
- [x] More than one observer may exist in the same realm at once — one per domain a consumer holds, regardless of how many concurrent occupants that domain admits — each independent, each with its own registered-extensions source and its own domain key, each released independently.
- [ ] Resolving a URL several domains deep is a wave of independent per-domain resolutions, not one event: a deeper domain's own observer exists and reports only once the runtime has mounted the route owner whose zone contains it and the framework router has created that deeper domain's own observer, this feature publishes no signal asserting that an address resolved end to end, and a domain several steps deeper reporting nothing yet is indistinguishable, at any shallower domain, from that deeper domain's own wave simply not having arrived.
- [x] The back-projection helper issues exactly one `push` or `replace` call, whichever verb the caller supplied, that writes the given domain key's own delta, removes the entries under exactly the domain keys `clearedDomainKeys` names, and leaves every entry under every other domain key, and every entry under this domain key the delta does not name, exactly as it was.
- [x] `clearedDomainKeys` is applied exactly as given, never inferred: from `/en?screen=tenants;tenantId=ABC&tabs=contacts&legend=right&modal=create-contact`, a call for the `screen` domain naming `[tabs]` removes `tabs=contacts` and keeps `legend=right` and `modal=create-contact`, because only `tabs` was named; a named key no entry carries removes nothing, and the call still issues its one write; a named key that is not a valid `name` throws `invalid-domain-key` before anything is written; and a call naming no domain key to clear removes no entry outside the calling domain key's own delta, whichever tokens that delta removes or replaces.
- [x] The back-projection helper's single write carries the caller's given page hash when the caller passed one, including an empty string clearing the hash, and the URL's own current page hash, unchanged, when the caller passed none — never a second history call to carry the hash separately.
- [x] A `reordered` list that is not exactly a permutation of the domain's own surviving entries — one short, one too many, or naming a token twice — throws before anything is written, and the location is unchanged. The survivors it must name are the tokens the *current* location carries, so a delta that both replaces `a` with `c` and reorders names `a`, not `c`, and a delta that both adds `c` and reorders never names `c` at all.
- [x] A `replaced` pair whose `oldExtension` no entry under that domain key currently carries throws before anything is written, and the location is unchanged — the entries under the delta's `clearedDomainKeys` included, since nothing is written for a replacement that never happened. This is not one of the absent-token cases the No-op note tolerates: a caller opening an entry at a position that does not yet exist expresses it as an addition instead.
- [x] A delta whose `added` list names an extension token already present under that domain key, or names one token twice, throws the codec's own duplicate-extension error and writes nothing — as does a `replaced` pair whose new token another entry under that domain key already holds. Reopening an entry under a token already present is expressed instead as a payload change, or as that token's removal and addition in the one delta.
- [x] Every call writes: an empty delta, or one naming only tokens the domain key does not carry, still issues exactly one `push` or `replace` of the composed list, so two consecutive empty deltas produce two identical history calls. This is what lets a caller write a page hash and nothing else; deciding whether anything changed is the consumer's, under §1.4's Binding obligation.
- [x] An entry under another domain key survives a write with its structure intact but in the codec's own canonical encoding, not byte for byte: `?other=x;q=%41&mine=a` comes back as `?other=x;q=A&mine=a`, while `;q=a%20b` keeps its escape. A query segment that never parsed as an entry at all — an OAuth `code`, an analytics `utm_*` — is the value that survives byte for byte.
- [ ] The framework router passes the helper the verb the settled action's history intent names — `push` for an action carrying `push` or no intent at all, `replace` for one carrying `replace` — so an opening action carrying `push` lets a back step close what was opened, and a closing action carrying `replace` keeps a back step afterward from reopening it; a settled action carrying `none` produces no helper call and no history write.
- [ ] The transition the back-projection helper's own history call produces carries no difference between the domain's entries and what is mounted there, so the framework router sends no chain for it, and nothing is mounted twice or re-initialized; the framework router suppresses none of the action effects of its own URL writes.
- [ ] For a URL transition the framework router sends one `unmount_ext` per removed occupant and one `mount_ext` per added occupant, each its own actions chain, removals dispatched before additions, uniformly in every domain; a removal that fails holds back no addition, and a request the domain's handler refuses, such as an Exclusive domain's `unmount_ext`, leaves the mounts as they are.
- [ ] The framework router reflects each settled report by applying the extensions it lists as mounted and unmounted in one back-projection call with the report's history intent, removing a departing host's nested domain entries in that same call, and reads neither the action type nor any cardinality of the domain; a report carrying `none`, and a report listing nothing mounted and nothing unmounted, produce no call.
- [ ] This feature holds no registry of route owners, executes no mount or unmount itself, at any domain, and defines no occupancy state machine; the framework router pursues the agreement between the URL and the mounted set, per the Binding obligation (§1.4), recursively at every routed domain, on top of the primitive, the signal, and the helper this feature publishes, reaching every mount and unmount only through `mount_ext` and `unmount_ext` action chains.
- [ ] A domain's occupancy cardinality — how many route owners a domain may hold simultaneously, and how a race between two mounts resolves — is decided entirely by the runtime that executes the framework router's action chains; this feature carries no notion of exclusive versus concurrent occupancy, and resolves no mount race of its own, at any domain.
- [x] A domain key with no observer currently reading it is inert, not an error and not a fallback state; it is resolved correctly the moment a domain that reads it comes to exist, because every observer reads the URL's current, live state rather than a value captured earlier.
- [ ] Teardown of the occupant whose zone contains a nested routed domain — part of the parent action's own execution — releases that nested domain's observer through the framework router, so no observer keeps resolving and reporting against a domain key or a registered-extensions source whose owning zone no longer exists.
- [x] Observer creation and the back-projection helper each throw `invalid-domain-key`, synchronously and before anything is resolved or written, for a domain key that is not a single valid `name` — `screen.tenants.tabs` among them.
- [x] The console layout worked example resolves and back-projects exactly as pictured:

  ```
  /en?screen=tenants;tenantId=ABC
     &tabs=contacts
     &modal=create-contact
  ```

  `tabs` is the route the `tenants` extension's own zone declares for its nested tabs domain, carrying no reference to `screen` or to `tenants`, because a domain key never restates an ancestor; `modal` is the console's own root domain. The `screen`, `tabs`, and `modal` domains' own observers each resolve the one entry under their own key. An implementation **MUST** reproduce this example as one of its own acceptance scenarios.

- [x] The structural reset worked example resolves exactly as pictured, in both directions:

  ```
  before: /en?screen=tenants;tenantId=ABC&tabs=contacts&modal=create-contact
  after:  /en?screen=settings&modal=create-contact
  ```

  A `mount_ext` of `settings` into the `screen` domain, carrying the history intent `push`, replaces `tenants`; its execution releases the nested `tabs` domain's occupant and observer as part of that same action. The framework router reflects the one settled action with one back-projection call for the `screen` domain, carrying `{oldExtension: tenants, entry: {extension: settings, params: []}}` in the delta's replaced list and `[tabs]` in its `clearedDomainKeys`, with the verb `push`; the helper's own single call swaps `screen=tenants;tenantId=ABC` for `screen=settings` at that same position and removes `tabs=contacts`, while `modal=create-contact` is untouched, because `modal` is not among the named keys. Had the call named no key to clear, `tabs=contacts` would have survived as a stranded entry. An implementation **MUST** reproduce this example as one of its own acceptance scenarios.

- [ ] Leaving the `tenants` screen in the structural reset worked example above never rewrites the entry the user left: after the `push` write, the history entry before it still reads `/en?screen=tenants;tenantId=ABC&tabs=contacts&modal=create-contact`, with the nested `tabs` occupant's own entry intact. A Back step lands on it, and the framework router turns the reported transitions into `mount_ext` chains carrying the history intent `none`, bringing the `tenants` screen back together with its nested `contacts` tab, each reading its own entry's own parameters — `tenantId=ABC` included — and makes no back-projection call for them; a Forward step afterward returns to `/en?screen=settings&modal=create-contact` the same way, again with no history write.

- [x] Nesting inside a domain holding several occupants resolves exactly as pictured:

  ```
  /en?widgets=line-a;range=7d
     &legend=right
     &widgets=line-b;range=30d
  ```

  `legend` is the route the `line-a` occupant's own zone declares for its nested legend domain, and that domain's own observer resolves the one entry addressed to it. `line-b` carries no legend entry; were its own zone to host a legend domain while `line-a`'s is live, that domain would declare a route of its own, distinct from `legend`, because no two routed domains live in the page share a route (DESIGN §2.3, O1). A domain key with no live observer is simply inert, not an error.

The helper reassigns the domain's own two entries to the same two positions they already occupied, in that new order, triggering no structural reset; every other domain's own entries are untouched. The domain's own observer reports a transition whose diff carries `Reordered: true` and empty `Added`/`Removed`/`Payload-changed`.
